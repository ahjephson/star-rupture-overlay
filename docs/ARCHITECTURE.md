# Architecture

## Components and ownership

The UI thread owns the window, tray icon, embedded fonts and GDI resources. A persistent worker retains a query/read-only game handle and checked runtime references, publishes observations under a mutex and posts a window notification. Rendering and window operations remain on the UI thread.

| Crate | Responsibility |
| --- | --- |
| wave-overlay | Native window, tray controls, rendering, observation consumption and application lifetime |
| assets | Offline archive discovery, schema-driven property reading and recipe graphics extraction |
| reader | OS query/read boundary, runtime discovery, allocation/session guards, bounded caches and sampling |
| wave-core | Configuration, observation validation and native wave timing calculations |
| observation-model | Bounded envelopes, sequence/generation validation and HUD presentation |

The live data flow is game memory → reader → validated observation → timing calculation → HUD presentation. Recipe setup combines installed game archives with a native type schema, then writes a validated local asset cache for the recipe renderer. Shared Rust structs and enums define player, world, clock, pause, phase and timing data. All application crates inherit the workspace release version. The observation validator checks its schema and `READER_CONTRACT_VERSION` independently of the release version.

The worker moves typed observations through validation into shared UI state. The 64 KiB observation limit accounts for the envelope, boxed world payload and allocated string capacities. Named Heat settings and a native-stage enum express timing data; fixed-size arrays hold coordinates and substage identifiers in documented order. The HUD presenter compares process, session, world, phase and configuration fields directly, retaining a debounce key until those fields change. JSON is used for settings, discovery cache files and explicit diagnostic output. Configuration file validation preserves accepted compatibility keys and produces operational settings containing only the cache directory and live-reading switch.

## Reader lifetime and observation guards

Closing the app cancels the worker and joins it before releasing shared state. A condition variable waits until the next sampling or attachment deadline and wakes when cancellation is requested. The worker also checks cancellation before memory reads, process enumeration and executable-hash chunks. Monotonic budgets bound discovery to 60 seconds and ordinary sampling operations to five seconds. Cancellation is cooperative; an individual blocking OS call can delay shutdown.

Menu checks target 50 ms; complete world and timer observations target 250 ms. They run serially, so a full observation can defer a menu check. Menu timestamps affect layout only. Independent timer evidence establishes countdown freshness and simulation pause.

Observations carry a bounded read window, process creation identity, executable hash, session generation and sequence. World/object allocation identities and native timing configuration are validated before use. Typed observation-conflict errors discard torn phase/configuration reads without refreshing evidence. Other identity failures invalidate the observation before reacquisition. Cache files contain bounded discovery hints checked against live identities. Checked player/context offsets, boolean masks and clock offsets are resolved into named runtime bindings at attachment; sampling retains identity and numeric-bound checks.

Cold discovery reads the executable headers and section buffers through the existing guarded query/read handle, in chunks of at most 1 MiB. It does not allocate a second whole-image buffer. The section image and configuration-resolution cache are released before the registry walk. Each temporary discovery cache retains at most 256 pages of 64 KiB (16 MiB), clearing the cache when the next read would exceed that limit. Oversized reads bypass the cache. Sampling retains direct process reads and allocation guards.
## Application preferences and lifecycle

The reader worker publishes process presence separately from validated wave observations. A retained process handle confirms exit even while runtime discovery or observations are unavailable. A session becomes eligible for game-exit actions after the reader publishes Ready; only confirmed process exit ends that session. Presence updates supply tray and About status independently of observation freshness and timing guards.

Settings, About, licence notices and the optional game-exit prompt are native modeless dialogs created on demand. The UI message loop routes keyboard input through IsDialogMessage. Dialog state uses separate stable allocations, and owned windows release resources on close. Preferences load once and change in memory after their file is replaced successfully. Startup registration uses the current user's Run key; a preference-file failure restores the previous registration. Desktop shortcuts use IShellLink and the user's Windows Desktop location. Settings distinguishes missing shortcuts, the current target, another recognised app copy and unrelated links. Recognised copies require the app description, a current or legacy executable name and matching launch/configuration arguments, including when the old executable is missing. Update shortcut writes a temporary link with the current target, working directory and icon, then replaces the unchanged previous link. Creating a new link does not replace an existing file. Shortcut changes are independent of preference Save and Cancel.

The desktop shortcut passes `--launch-game`, while startup registration omits it. A second instance forwards launch requests to the existing UI window. Requests wait for confirmed absence, ask Steam to launch the game and suppress repeats for up to two minutes.

## Wave timing and presentation

Timer fields are resolved from bounded native save/load methods and checked against reflected layout boundaries. Active-stage readers validate getter layouts and progress arithmetic. A session cache retains the controller proof after a bounded 64 KiB discovery near the owned phase methods; sampling checks that proof and the effective world time-dilation getter. The original compiler form retains its previously verified cap check. Uncalibrated settings remain unavailable. Pre-wave accepts the game's exact unset start-clock sentinel; later stages require a valid start time.

Waiting uses a directly verified native countdown. Active Heat timing uses native progress and inverse duration, retaining float32 accumulation, delta clipping and transition-tick limits. Actor deadline drift is diagnostic only. Normal-menu simulation pause requires pauser/delay/clock evidence. Local wave arrival and exact audiovisual cues are not independently established.

| Native phase | HUD label | Countdown target |
| --- | --- | --- |
| Waiting | STABLE | Rupture |
| PreWave | PRE-WAVE | Rupture |
| Moving | APPROACHING | Next native phase |
| Fadeout, elapsed time below 7 seconds | INCINERATING | 7-second display boundary |
| Fadeout, elapsed time at least 7 seconds | COOLING | Native Fadeout end |
| Growback | GROWBACK | Next native phase |

Fadeout elapsed time is its validated native duration minus native remaining simulation time. INCINERATING and COOLING are presentation labels within the same native phase. Unsupported substage timing retains FADEOUT with `--:--`.

The HUD floors seconds and suppresses an isolated one-second upward rounding correction within an unchanged phase/session. A second independent observation confirms that correction. The presenter resets its debounce when the displayed target changes. Countdowns advance with observed simulation time; timer evidence older than five seconds becomes unavailable. Native render diagnostics and presentation tests cover geometry, colours, glyph counts and play/menu anchors.

The recipe panel retains the catalogue, font and shared decoration images while ready. It loads output and ingredient pixels from the validated local cache for the union of up to three selections, retains shared images when toggling pins, and releases item pixels on clear or disable. The active image cache is limited to 8 MiB; dimensions, file lengths and safe names are checked before allocating each pixel buffer. Repeated observations of the same selected recipe reuse its pixels. Renderer diagnostics exercise every catalogue recipe, cache release and repeated selection alongside pixel output checks.
## Native API boundary

GDI objects use ownership guards that restore selected objects before release. The UI retains its render bitmap and memory device context until the client dimensions change. Rendering tests compare reused and resized surfaces with fresh pixels and check GDI handle counts after cleanup.

Win32 process handles close through RAII and remain on the worker thread using `Rc`. Cancellation and deadlines use thread-safe shared state. Reads validate pointer/size bounds before `ReadProcessMemory`. The reader checks the executable filename and retains its actual SHA256 in process, observation and asset-cache identities. It attempts live discovery on other builds; unfamiliar layouts or native timing remain unavailable. Windows supplies the installation path. The reader opens the game with query/read permissions under standard user privileges.

The font-count output for `AddFontMemResourceEx` uses writable raw storage even though the generated binding declares a const pointer. A shared reference would permit an invalid aliasing assumption for this output parameter. See the [Win32 font API contract](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-addfontmemresourceex).

## Window positioning and stacking

The HUD is an independently owned top-level window, normally in the ordinary window band. It positions its own HWND immediately above the validated game window without activation. Position and resize operations preserve ordering. Windows above the game remain above the HUD, including partial overlaps. For a non-topmost game, moving focus to another monitor leaves the HUD over the visible game; an application covering the game also covers the HUD.

Invalid, hidden or minimized game windows hide and demote the HUD. A topmost game is followed in the topmost band only while its exact window is foreground. Focus loss hides and demotes the HUD; return to a non-topmost game restores ordinary-band positioning. Synchronization rechecks foreground and band membership before accepting the result. This applies to both the countdown and recipe panel. The supported Fullscreen setting, Alt-Tab and switching to Borderless follow the [display compatibility scope](COMPATIBILITY.md). Menu layout moves it below the menu border; unlocked manual placement overrides automatic positioning until reset.

Desktop foreground, restore and reorder notifications use `SetWinEventHook` with `WINEVENT_OUTOFCONTEXT` and `WINEVENT_SKIPOWNPROCESS`. The callback coalesces events into a posted message without accessing application state or game memory. The UI handler reuses the last validated game HWND and rendered frame without acquiring the reader mutex or recalculating timing/geometry. Thread-affine RAII disables the target before unhooking. Registration failure retains the 100 ms UI timer fallback. See the [Win32 notification contract](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwineventhook).

Notification delivery and desktop composition are asynchronous, so visible updates depend on their scheduling.

## Native diagnostics

The optional [recipe tracker](FEATURES.md#recipe-research-sidebar) shares the worker but keeps its request generation, local asset cache, counters and window separate from wave observations. The first enabled connection validates an existing cache or generates a bounded native type schema and starts the same Rust executable in its internal asset-preparation mode. A kill-on-close Windows job owns this temporary process tree, preserving bounded cancellation and isolating archive parser failures. No setup tool, runtime or native decompressor is downloaded or unpacked. Archive preparation validates the supported TOC structure, table and block bounds, uncompressed data and complete coverage of discovered research assets. Actual TOC hashes are recorded as provenance rather than used as a content allowlist. Game archive metadata and prepared-file hashes guard cache reuse; complete generations replace the receipt atomically. The UI loads only the worker-published ready generation and registers its font in-process. Hover capture and research reads remain read-only. Connection setup resolves the UI manager and reflected layouts; shortcut handling follows player-owned layout/menu/widget references and never performs global discovery. Clearing or session reacquisition invalidates pending results. Recipe data does not advance or refresh wave evidence.

`--self-test-stacking` uses four owned off-screen windows. It covers separate/overlapping regions, partial coverage, repeated synchronization, focus return, manual placement, hidden/minimized/destroyed targets, foreground-only topmost following, topmost covering windows, simulated focus loss/return and mid-sync focus changes, and ordinary-band recovery while preserving foreground focus.

`--self-test-window-events` uses two owned off-screen windows and the real callback/posted-message handler. It performs 20 repairs with the reader mutex held and the UI timer disabled, verifies unchanged focus and checks that teardown stops delivery. This diagnostic measures the callback/message path; real game/desktop composition latency requires a live check.

Additional diagnostics check the hidden native window, rendered HUD states and embedded icon extraction/loading. `--self-test-dialogs ABSOLUTE-DIRECTORY` checks native dialog controls, preference Save/Cancel/failures, connection refresh and cleanup, with local captures and isolated preference files. These diagnostics operate on owned fixture windows. Live reader and manual appearance checks remain separate; see [release validation](RELEASING.md).


## Recipe tracking

Broad object discovery is confined to connection binding setup and its two bounded recovery attempts, plus native type-schema generation when the derived asset cache is missing or invalid. Normal capture, clearing and menu reopening do not enumerate the object registry. They follow the current local player's viewport/game-instance ownership, the UI manager's policy and matching attached layout, then the menu stack's displayed inventory screen. The visible recipe table is resolved through that screen's owned widget references. Recipe rows come from the table's crafter and recipe panels. Missing, ambiguous or unattached player layouts are unavailable, never treated as a closed station. The menu stack's validated empty displayed-widget reference establishes closure.

All links, local-player ownership, object classes/serials, visibility and collection headers/contents are reread before an observation is accepted. Opening/closing a menu replaces its references naturally; no per-opening global warmup or negative registry scan is needed. The recipe reader diagnostic asserts zero global scans across its context/capture/sample checks.

The reader worker retains exclusive ownership of the process handle and performs all game reads. Reflected layouts resolved for the attached build establish the recipe owner, requirements arrays and recipe-row references. Native widget code establishes cached Slate hover and owning-player context bindings; Capture checks the recipe table's native activation flag, owning player, visible widget ancestry and active inventory-screen root, with allocation and pointer rereads. A validated outside-station keyboard request clears all pins while the game retains focus; it does not require a cursor position. Mouse requests outside the station preserve the selection. Station-row capture still requires the cursor to remain over the requested target. Read failures preserve the pin. Fully submitted tracking updates remove only the affected pin. A pinned recipe absent from a stable, reread active research list also clears after validating the same world, owner and allocation identities; this removes the inactive selection without inferring an unlock from absence alone. In the station, capture validates row class, player weak reference, widget allocation, visible station ancestry, native hover flag and recipe identity before retaining a native recipe asset ID. It does not invoke widget functions or debug unlock handlers. Persistent tracking reads the recipe owner's counters with allocation/header/content and world/owner rereads. The pinned recipe-record location is a hint revalidated on reuse. Bag quantities join current-character owned handles to the matching item store, with allocation, handle, count and array rereads. Bag reads do not include depot stock. Missing bag evidence remains unknown. Required amounts come from the matching native reference pack; ingredient mismatches and duplicate or invalid counts stay unavailable.

Pin and clear requests carry a generation. A cleared or replaced request rejects delayed worker results. Process/world reacquisition clears the pin. Failed shortcut reads leave a diagnostic message in the local app log. Recipe sampling is bounded and shares the existing worker, cancellation and process guards; it does not add a watcher, second resident reader or MCP dependency. Each recipe has its own click-through window and shares the bounded image cache. A separate non-activating 28-pixel window captures only its close target. All recipe and close windows follow the existing game window ordering rules. A generation change retags remaining pins, rejects delayed reads and prevents a closed panel from being resurrected. Wave observation contracts and timing calculations are independent of recipe tracking.


Recipe cache receipts contain the installation path, archive sizes/timestamps and per-file prepared-asset hashes. Only complete validated generations replace the current receipt. Archive metadata checks are not a full hash of every installed archive; the prepared catalogue must match the executable hash retained by the process reader. Native schema generation has a two-minute read budget. The hidden preparation process runs under a kill-on-close Windows job with a five-minute timeout. Setup shares the observation worker, so long preparation can leave timing temporarily stale before ordinary sampling resumes.

The foreground-scoped mouse hook forwards every event and only posts physical left-button coordinates and native timestamps to the UI thread. Double-click recognition uses Windows time and distance settings, excludes non-game surfaces and requires a visible game cursor. The worker resolves mouse captures through the reflected RecipeImage and RecipeName references, validating ownership, widget ancestry, native hover and allocation rereads; ingredient and INSERT controls are not pin targets. Hook teardown clears its target before unhooking. No game input is injected or suppressed.

The reflected bReplInPauseMenu flag controls recipe layout independently of inventory/station menus and timer pause evidence. The normal 96-unit panel uses 64-unit ingredient icons with 74-unit rows. The control rail starts below the scaled tab edge and reserves the close target plus a clear gap before the icon at every scale. Measured name text fits a two-line area before the ingredient list. Every panel uses the group height determined by the largest ingredient count; the leftmost card alone has a raised top tab, the rightmost alone has the lower corner cut, and a single card receives both. Plain top edges align to the lower tab baseline; all bottom edges share the group baseline. A continuous two-pixel border follows each shape, and roles are recalculated after pin changes. All selected panels use one scale derived from the requested size, maximum ingredient count, client height and the pause-menu right gutter. The current layout reserves the outer 9.6 percent of the game client for pause-menu panels and keeps the right edge anchored at 14 pixels in both layouts. Groups that fit retain their requested scale. Width-limited groups use the available strip while reserving the same 14-pixel clearance at the menu edge; whole-pixel rounding is absorbed into the inter-panel gaps. A fit below the minimum readable scale hides the group. Closing the menu restores the requested scale. Close targets retain their 28-pixel hit area independently of the panel scale and reuse an owned copy of the native cursor last observed over the foreground game. A shared UI-thread cursor cache excludes the overlay and other apps, validates the cursor again after copying, and releases only its own duplicate on replacement, game change or shutdown. The standard arrow is a fallback until a game cursor is known. Close targets track mouse leave and redraw an amber/orange outline, tinted fill and cross only when the hover state changes. Hiding or moving a target clears its highlight. Repeated unchanged close-target refreshes do not move or reorder their HWNDs; a changed position or anchor is updated directly without an intermediate move behind the panel.
