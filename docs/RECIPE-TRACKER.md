# Recipe tracker

Version 0.2.7 provides offline recipe asset preparation and live research tracking.

## Operation

Open Settings and use the Recipe tracker section to enable the panel, change its shortcut, select an upper/middle/lower right position or choose 75–150% scale. The default shortcut is Alt+X. Hover over a recipe row in the station and press the shortcut once to pin it. Hover over another unfinished recipe and press it to switch. Use the shortcut on the same unfinished recipe to clear. Outside the station it clears a pinned recipe even while the mouse moves or recenters, and otherwise does nothing. In the station, no hovered row or a completed recipe leaves the selection unchanged. The tracker prepares its local assets when enabled and connected to a supported loaded world. Reopening the station uses its current menu references. Holding the keys does not repeat the action. Shortcuts register while the game has focus and are released when focus leaves it or the app closes. Conflicts appear in Settings.

The upright title icon uses the native half-opacity grey frame, rotated to point downward beyond the square. The title and icon identify the pinned research recipe. Vertical tiles show its research materials, submitted/required amounts and completed requirements. Those counts are research payments, not inventory or manufacturing inputs. A new panel appears only after a successful read; the previous panel remains visible while switching. The narrow panel keeps tracking after the station closes. Any positive bag quantity makes the fraction white and adds an orange count inside the tile; zero bag quantity makes it red. Counters align to the left inside each tile. Partial submitted amounts use two lines with the game's spacing, black outline and drop shadow. Invalid, changing or stale evidence displays unavailable counts. The panel closes automatically when the pinned recipe is completed.

## Automatic local setup

Users start the overlay and load a supported world. The app discovers the running game's location through its existing validated process connection. The reader worker produces the native type schema needed to decode the installed archives, then prepares the recipe definitions, icons and font. Users do not supply mappings, exports or an asset folder. Setup progress and retry instructions appear in Settings; the recipe panel stays hidden until a recipe has been read successfully.

The first setup works offline. The app generates a bounded native type schema and runs its own Rust executable in a hidden, cancellable job to discover recipes, resolve names and references, and decode the supported game icons and font. No external tool, SDK, runtime or native decompressor is downloaded or required. See [setup dependencies](DEPENDENCIES.md#recipe-setup-components) for the retained Rust source and notices.

Assets and native schemas are stored under `%LOCALAPPDATA%/StarRuptureWaveOverlay/recipe-cache`. Completed generations have a receipt containing the installation path, archive sizes/timestamps and per-file asset hashes. Only complete validated generations replace the current receipt. Missing, changed or damaged assets cause preparation again; old generations remain recoverable. Archive metadata checks are not a full hash of every game archive. The supported executable hash remains independently enforced by the reader.

Preparation shares the reader worker and uses query/read-only game access. Normal wave observations start before asset preparation; a long setup can make timing temporarily unavailable until sampling resumes. Setup failure leaves wave sampling available. Disabling the tracker prevents setup; disabling it during a helper run or exiting the app stops the owned setup process tree. Enabling it again retries a failed preparation. Setup processes run hidden under a kill-on-close Windows job with a five-minute timeout; native schema reads have a separate two-minute read budget and cancellation checks.

Native fonts are registered only in the overlay process. Maintainers can use `scripts/Import-RecipeAssets.ps1` for local exported test fixtures, which stay outside Git and release archives.

## Validation

- `--self-test-asset-setup ABSOLUTE-DIRECTORY` exercises the production first-run path in an isolated cache, then checks recipe renders, font selection and 24 world observations. Repeating it checks cache reuse.
- `--self-test-asset-disabled ABSOLUTE-DIRECTORY` checks 24 world observations with setup disabled and verifies that no recipe cache is created.
- `--self-test-asset-cancel ABSOLUTE-DIRECTORY` starts only owned fixture processes and verifies that cancellation stops the entire process tree.
- Run the usual formatting, strict Clippy, workspace tests, dependency/vendor checks and release/package regressions.
- `--self-test-recipes ABSOLUTE-DIRECTORY` checks native shortcut conflict/release handling, actual Nippo font selection, partial/completed/stale renders and premultiplied alpha, using synthetic counters and owned offscreen windows. It does not read the game or start a normal overlay.
- `--self-test-recipe-warmup ABSOLUTE-DIRECTORY` runs the production worker for 24 world observations with connection preparation enabled and no shortcut requests. It verifies unchanged selection and joined shutdown; local logs record connection setup timing.
- `--self-test-dialogs ABSOLUTE-DIRECTORY` checks native settings defaults, Save, Cancel, invalid/file-failure paths and recipe control persistence using isolated preferences.
- `--self-test-recipe-reader ABSOLUTE-DIRECTORY [NATIVE-RECIPE-ID]` measures a bounded hover scan and makes three finite, guarded research observations plus bag inventory against a supported running game. It defaults to Biofilament; an explicit catalogue recipe ID also permits checking validated absence after completion. It records any visible hovered candidate without pinning it, submitting items, opening windows or changing the running overlay. An unavailable candidate outside the station is expected and does not verify hover capture.
- Manually verify Alt+X over the recipe icon, material tiles and row space; scrolling and closing/reopening the station; tracking after walking away; partial submissions, completion and clearing; shortcut changes/conflicts; focus changes; scale and placement. Automated counter reads do not establish those manual results.

## Implementation

Broad object discovery is confined to connection binding setup and its two bounded recovery attempts, plus native type-schema generation when the derived asset cache is missing or invalid. Normal capture, clearing and menu reopening do not enumerate the object registry. They follow the current local player's viewport/game-instance ownership, the UI manager's policy and matching attached layout, then the menu stack's displayed inventory screen. The visible recipe table is resolved through that screen's owned widget references. Recipe rows come from the table's crafter and recipe panels. Missing, ambiguous or unattached player layouts are unavailable, never treated as a closed station. The menu stack's validated empty displayed-widget reference establishes closure.

All links, local-player ownership, object classes/serials, visibility and collection headers/contents are reread before an observation is accepted. Opening/closing a menu replaces its references naturally; no per-opening global warmup or negative registry scan is needed. The recipe reader diagnostic asserts zero global scans across its context/capture/sample checks.

The reader worker retains exclusive ownership of the process handle and performs all game reads. Build-pinned reflected layouts establish the recipe owner, requirements arrays and recipe-row references. Native widget code establishes cached Slate hover and owning-player context bindings; Capture checks the recipe table's native activation flag, owning player, visible widget ancestry and active inventory-screen root, with allocation and pointer rereads. A validated outside-station request clears the current pin while the game retains focus; it does not require a cursor position. Station-row capture still requires the cursor to remain over the requested target. Read failures preserve the pin. Fully submitted tracking updates clear it. A pinned recipe absent from a stable, reread active research list also clears after validating the same world, owner and allocation identities; this removes the inactive selection without inferring an unlock from absence alone. In the station, capture validates row class, player weak reference, widget allocation, visible station ancestry, native hover flag and recipe identity before retaining a native recipe asset ID. It does not invoke widget functions or debug unlock handlers. Persistent tracking reads the recipe owner's counters with allocation/header/content and world/owner rereads. The pinned recipe-record location is a hint revalidated on reuse. Bag quantities join current-character owned handles to the matching item store, with allocation, handle, count and array rereads. Bag reads do not include depot stock. Missing bag evidence remains unknown. Required amounts come from the matching native reference pack; ingredient mismatches and duplicate or invalid counts stay unavailable.

Pin and clear requests carry a generation. A cleared or replaced request rejects delayed worker results. Process/world reacquisition clears the pin. Failed shortcut reads leave a diagnostic message in the local app log. Recipe sampling is bounded and shares the existing worker, cancellation and process guards; it does not add a watcher, second resident reader or MCP dependency. The recipe panel has its own click-through window and rendering resources and follows the existing game window ordering rules. Wave observation contracts and timing calculations are independent of recipe tracking.
